# Security checklist before real users

> **Hosting-mode note:** The **Cloudflare** section and the checks forbidding all router forwards apply to the Tunnel option. Direct hosting instead allows only the exact Caddy executable on TCP 80/443 while continuing to block and never forward port 8080. Use the direct-host security boundaries in [DIRECT-HOSTING.md](./DIRECT-HOSTING.md) and do not combine the two network configurations.

Do not treat a successful `/health` response as a security review. Complete every item below before production use.

## Windows host

- [ ] Windows is supported, fully patched, and protected by a strong owner login and MFA where available.
- [ ] BitLocker protects the system/data disk, and recovery keys are stored somewhere separate.
- [ ] The host uses a fixed NTFS disk and does not live-sync the SQLite folder.
- [ ] Sleep and hibernation are disabled while plugged in; the display may turn off.
- [ ] Microsoft Defender remains enabled with current definitions.
- [ ] RDP, SMB, PowerShell remoting, and remote administration are not exposed to the internet.
- [ ] The router has no Babcord, 8080, database, RDP, or SMB port forwards; UPnP did not create one.
- [ ] Only trusted Windows administrators can read `C:\ProgramData\Babcord`.
- [ ] At least one completed backup exists on a separate encrypted device.

## Application and network

- [ ] Node.js 24 and server dependencies come from official/trusted sources and have received security updates.
- [ ] `BABCORD_HOST` is `127.0.0.1`; status reports **Loopback only**.
- [ ] The Babcord inbound firewall block rule exists; no broad allow rule overrides the intended isolation.
- [ ] `BABCORD_SECRET` and the recovery pepper are long random values generated by setup, not example values.
- [ ] The bootstrap admin has signed in, saved recovery codes, changed password, and had its bootstrap secret cleared.
- [ ] The protected mandatory Babcock server exists and cannot be left or deleted by normal accounts.
- [ ] CORS accepts only `Origin: null` and the exact Babcord HTTPS origin. A `null` origin alone grants no access.
- [ ] Authentication uses bearer tokens, not cross-site cookies, and every privileged API checks permissions server-side.
- [ ] WebSocket sessions authenticate and reconnect without putting long-lived tokens in URL logs.
- [ ] `/health` reveals no secrets, database paths, usernames, counts useful for attack, or stack traces.
- [ ] Production errors never return stack traces or raw SQL to clients.

## Cloudflare

- [ ] The Cloudflare account uses MFA and has safe account-recovery methods.
- [ ] Only `babcord.withermask.net` points to the named Tunnel; no DNS record reveals the home IP.
- [ ] The connector is healthy and its token has never been committed, emailed, or posted.
- [ ] There is no Cloudflare Access browser gate in front of the `file://` API/WebSocket.
- [ ] Private API, health, attachment, realtime, and manifest routes are not cached.
- [ ] The Tunnel targets only `http://127.0.0.1:8080` and has a catch-all 404 if locally managed.

## Accounts, moderation, and privacy

- [ ] Registration/login/message/upload rate limits are verified under load.
- [ ] Passwords and recovery codes are hashed; logs never contain either, bearer tokens, or session secrets.
- [ ] Global-admin actions are immutable in audit logs and cannot be hidden by the acting admin.
- [ ] Opening a DM as an admin requires a reason and records the actual admin identity.
- [ ] Messages sent as `Administration` reveal only that handle to users while preserving the real admin internally.
- [ ] Deleted visible messages retain original content only in protected logs for the remainder of 30 days, with deletion actor/time.
- [ ] Every global admin receives the daily five-day purge warnings and can review/export the expiring batch.
- [ ] At least one encrypted `.bclog` export was opened with `Open-BabcordLogExport.ps1`; wrong-password and damaged archives were rejected.
- [ ] The retention job permanently purges expired protected content and reports completion.
- [ ] Server moderators can see only their own server's logs; platform DM logs require the explicit investigation flow.

## Attachments and updates

- [ ] Image/file size and four-per-message limits are enforced before and during upload.
- [ ] `.zip`, `.html`, and `.htm` remain unfiltered as required, but always download with safe `Content-Disposition` and `X-Content-Type-Options: nosniff` headers.
- [ ] Stored filenames are generated; supplied filenames cannot escape the attachment directory.
- [ ] Private attachment downloads re-check conversation/channel permission.
- [ ] The local launcher loads the current HTTPS-hosted client, honors minimum-version update notices, and offers the server-hosted launcher download when the launcher itself must change.
- [ ] Manifest asset hashes were checked during release verification; rollback uses the retained prior server release because Version 1 has no offline client cache.
- [ ] An unavailable server immediately produces the designed client message and never claims an unsent message succeeded.

## Recovery and release readiness

- [ ] Windows restart automatically returns all three Babcord tasks and the Tunnel to healthy status.
- [ ] Power/internet/Tunnel loss and recovery have been tested from Windows Chrome and Chromebook Chrome.
- [ ] A backup has passed a full restore drill, including attachments.
- [ ] Code rollback and client-bundle rollback have both been rehearsed.
- [ ] Around 100 users and expected concurrent connections have been load-tested without blocking moderation or logging.
- [ ] The clean light/dark UI, keyboard access, permission errors, offline states, and intentional voice placeholders have passed release acceptance.
